1. Application Title and Problem Addressed

Application Title

StudyGroup — A University Study Group Finder web application.

Problem Addressed

University students frequently struggle to find study partners or form study groups for their courses. There is no centralized, easy-to-use platform to connect students who are taking the same classes. Students rely on informal word-of-mouth, scattered social media groups, or chance encounters — making it difficult to find consistent, organized study support when they need it most, especially before exams or for challenging coursework. StudyGroup solves this by providing a single platform where students can discover, create, join, and manage study groups for any course.

7. Testing Approach Used in Part 2

Testing Methods

  1. Build verification: npm run build and npm run typecheck run after every batch of fixes to ensure no compilation or type errors.
  2. Code inspection: Every source file was read and analyzed for functional, security, data, usability, and code-quality issues.
  3. Edge-case analysis: Considered empty input, whitespace-only input, capacity boundaries, duplicate joins, and error states.
  4. Security audit: Reviewed RLS policies for each table, checked for authorization bypasses, exposed secrets, and unsafe data access patterns.
  5. Performance review: Identified N+1 query pattern in the group detail page member list.
  6. Retest after fix: Each fix was verified by build + typecheck, and the logic was re-read to confirm correctness.

9. Code and Architecture Analysis

Project Organization

The project follows a clean separation: src/lib/ for Supabase client and auth context, src/components/ for UI components, and supabase/migrations/ for database schema. This is a reasonable structure for a small React app.

Strengths

  • TypeScript types defined for all data models (StudyGroup, Membership, GroupWithCount)
  • Auth context with useAuth hook — clean pattern for session management
  • RLS policies on all 3 tables with per-verb CRUD separation
  • Parallel data fetching with Promise.all in BrowseGroups and MyGroups
  • Consistent UI design language: gradient brand, rounded cards, hover effects
  • Responsive grid with appropriate breakpoints

Weaknesses Found

  • N+1 query in GroupDetail: Member emails fetched one-by-one instead of batched (fixed)
  • No input trimming: Whitespace-only input stored in database (fixed)
  • No delete confirmation: Destructive action with no safety check (fixed)
  • No capacity recheck on join: Race condition could exceed group capacity (fixed)
  • Silent error on leave: My Groups page ignored leave failures (fixed)
  • Dead code: Unused icon re-export in BrowseGroups (fixed)
  • Creator not auto-joined: Group creators don't appear in their own member list (unresolved)
  • Raw error messages: Database errors shown directly to users without friendly formatting (partially unresolved)

Dependencies

Dependencies are appropriate and minimal: React 18, Supabase JS client, Lucide React icons, Tailwind CSS. No unnecessary or bloated packages. No secrets are committed to source code — Supabase credentials are loaded from environment variables via import.meta.env.

D1 — Delete Confirmation (High)

Before: The delete handler immediately deleted the group with no confirmation.

// BEFORE (GroupDetail.tsx) const handleDelete = async () => { setActionLoading(true); const { error: delErr } = await supabase.from('study_groups').delete().eq('id', groupId); ... };

After: A confirmation dialog now appears before deletion proceeds.

// AFTER (GroupDetail.tsx) const handleDelete = async () => { if (!window.confirm('Are you sure you want to delete this group? This cannot be undone.')) { return; } setActionLoading(true); setError(null); const { error: delErr } = await supabase.from('study_groups').delete().eq('id', groupId); ... };

Retest: Build passed (0 errors). Typecheck passed. Logic verified — delete only proceeds after user confirms.

D2 — Capacity Race Condition on Join (High)

Before: Join inserted a membership without rechecking current member count.

// BEFORE (GroupDetail.tsx) const handleJoin = async () => { setActionLoading(true); const { error: joinErr } = await supabase .from('memberships') .insert({ group_id: groupId, user_id: user?.id }); ... };

After: A count query checks capacity before the insert is allowed.

// AFTER (GroupDetail.tsx) const handleJoin = async () => { setActionLoading(true); setError(null); const { data: memberData, error: memberErr } = await supabase .from('memberships') .select('id', { count: 'exact', head: true }) .eq('group_id', groupId); if (memberErr) { setError('Could not check group capacity.'); ... } const currentCount = memberData?.length ?? 0; if (currentCount >= (group?.max_members ?? 0)) { setError('This group is full.'); ... } const { error: joinErr } = await supabase .from('memberships') .insert({ group_id: groupId, user_id: user?.id }); ... };

Retest: Build passed. Typecheck passed. Logic verified — capacity is checked before insert.

D3 — N+1 Query in GroupDetail (Medium)

Before: Each member's email was fetched with an individual .maybeSingle() query inside a Promise.all loop.

// BEFORE (GroupDetail.tsx) const emails = await Promise.all( memberList.map(async (m) => { const { data: profile } = await supabase .from('profiles') .select('email') .eq('id', m.user_id) .maybeSingle(); return { user_id: m.user_id, email: profile?.email ?? 'Unknown', joined_at: m.joined_at }; }) );

After: All emails are fetched in a single batched query using .in('id', userIds) and a Map lookup.

// AFTER (GroupDetail.tsx) const userIds = memberList.map((m) => m.user_id); const { data: profileData } = await supabase .from('profiles') .select('id, email') .in('id', userIds); const profileMap = new Map(); (profileData as { id: string; email: string }[] | null)?.forEach((p) => { profileMap.set(p.id, p.email); }); emails = memberList.map((m) => ({ user_id: m.user_id, email: profileMap.get(m.user_id) ?? 'Unknown student', joined_at: m.joined_at, }));

Retest: Build passed. Typecheck passed. Reduced from N queries to 1 query for member emails.

D4 — Input Trimming and Validation (Medium)

Before: Form fields were inserted as-is with no trimming; max_members was not clamped.

// BEFORE (CreateGroupModal.tsx) .insert({ title, course_code: courseCode, course_name: courseName, description, location, meeting_time: meetingTime, max_members: maxMembers, creator_id: user?.id, })

After: All text fields are trimmed; max_members is clamped between 2 and 100.

// AFTER (CreateGroupModal.tsx) .insert({ title: title.trim(), course_code: courseCode.trim(), course_name: courseName.trim(), description: description.trim(), location: location.trim(), meeting_time: meetingTime.trim(), max_members: Math.max(2, Math.min(100, maxMembers)), creator_id: user?.id, })

Retest: Build passed. Typecheck passed. Whitespace-only input is now trimmed.

D5 — Error Handling on Leave in My Groups (Medium)

Before: The leave handler ignored the error return value.

// BEFORE (MyGroups.tsx) const handleLeave = async (groupId: string) => { await supabase.from('memberships').delete().eq('group_id', groupId).eq('user_id', user?.id); fetchData(); };

14. What the Group Learned About AI-Generated Web Applications

Key Learnings

  1. A polished UI does not mean correct functionality. The app looked complete and professional, but code inspection revealed race conditions, missing validation, and silent error handling that would only surface under edge cases.
  2. AI-generated database code needs human review. The RLS policies were well-structured, but the AI missed auto-joining the creator to their own group and did not enforce capacity at the database level. Understanding what the database does is essential.
  3. Performance patterns matter even in small apps. The N+1 query pattern (one database call per member) would cause noticeable slowdowns with larger groups. Recognizing this pattern requires understanding how database queries work.
  4. Testing requires more than "it looks like it works." Systematic testing means trying empty input, boundary values, duplicate actions, network failures, and multi-user scenarios — not just clicking through the happy path.
  5. Web development knowledge is needed to evaluate AI output. Without understanding React state, Supabase queries, SQL constraints, and error handling patterns, the group could not have identified the issues found in this audit. AI accelerates development but cannot replace the ability to read and judge code.
  6. Input validation is a shared responsibility. The database has constraints (UNIQUE, NOT NULL), but the application layer must also trim, validate, and clamp values before sending them. Relying on only one layer leads to data quality issues.

Web Development Knowledge Needed to Evaluate AI-Generated Apps

  • Understanding React component lifecycle, hooks, and state management
  • Ability to read TypeScript types and identify type mismatches
  • Knowledge of SQL constraints, RLS policies, and database triggers
  • Recognizing common performance anti-patterns (N+1 queries, unnecessary re-renders)
  • Understanding of HTTP error handling and user feedback patterns
  • Ability to distinguish client-side checks from server-side enforcement
  • Familiarity with build tools and type checking to verify code correctness
